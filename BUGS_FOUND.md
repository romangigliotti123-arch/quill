### Clicking the key recorder and then leaving it (window close / app switch) makes the hotkey deaf for the rest of the session

**Area:** hotkey

**Failure:** 1. Menu bar → open Quill → Settings. 2. Click the dictation-key chip; it lights up and reads "Press a key", and `startRecording()` sets `QuillSettings.shared.isCapturingHotkey = true`. 3. Change your mind and leave with the mouse — click the window's red close button, or just switch back to the editor/terminal you were going to dictate into. Nothing calls `stopRecording()`: the only exits are a second click on the chip, a keyDown while Quill is frontmost, or the view being deallocated. 4. `isCapturingHotkey` stays true, and `EventTapHotkeyEngine.handle` returns at its capture guard for every single flagsChanged and keyDown. Hold, double-tap hands-free, Escape-cancel and ⌥⌫ are all dead — no HUD, no error, the titlebar pill and the menu still say "Ready". The recorder is never deallocated (AppDelegate holds `dashboard` for the app's lifetime, the closed window keeps its view tree), so this persists until the user happens to reopen the dashboard and press a key, clicks another sidebar row (which does release the section and clears the flag in `deinit`), or relaunches. A local NSEvent monitor cannot save it, because it only fires while Quill itself is frontmost — which is exactly not the case when the user has gone off to dictate.

**Evidence:** /Users/romangigliotti/Documents/Work/Projects/quill/Sources/QuillKit/Dashboard/Sections/SettingsControls.swift:401 `private func startRecording() { guard monitor == nil else { return }; QuillSettings.shared.isCapturingHotkey = true; isRecording = true; monitor = NSEvent.addLocalMonitorForEvents(...) }` — the class has no `didResignActive`, `viewDidMoveToWindow` or window-close handling anywhere (grep for resign/viewDidMoveToWindow in that file returns nothing); the only resets are `stopRecording()` (line 412) and `deinit` (line 325). /Users/romangigliotti/Documents/Work/Projects/quill/Sources/QuillKit/Hotkey/HotkeyEngine.swift:356 `if bindings.isCapturingHotkey { if machine.state != .idle { apply(...) }; return false }` — total deafness. /Users/romangigliotti/Documents/Work/Projects/quill/Sources/QuillKit/App/AppDelegate.swift:244 `if dashboard == nil { dashboard = DashboardWindowController() }` — the controller, window and view tree outlive the close.

**Fix:** The lifecycle half of the proposed fix is right; the deadline half is wrong as written and would create a worse bug.

Correct part: in `KeyRecorderControl`, call `stopRecording()` — not just clear the flag — from `NSApplication.didResignActiveNotification`, from `viewDidMoveToWindow()` when `window == nil`, and from the window's `willCloseNotification`. `stopRecording()` is the right call because it removes the monitor, clears the flag *and* resets `isRecording`, so the chip un-lights and the control's visible state never disagrees with the engine's. Losing first responder is not needed — this view never becomes first responder — and resigning active is a sound trigger precisely because capture can only ever complete while Quill is frontmost.

Wrong part: "give the flag a deadline in QuillSettings (a capture older than ~10s is over)". A deadline that expires the *flag* while the recorder is still listening is actively harmful. The local monitor does not stop the CGEventTap — the tap sits upstream of app delivery — so once the flag has expired but `monitor` is still installed, pressing ⌥ would both bind the key in the recorder and start a dictation in the engine off the same physical press. That is exactly the collision the flag exists to prevent (SettingsControls.swift:274-282). If a timeout is wanted at all, put it on the control: a `DispatchWorkItem` scheduled in `startRecording()` and cancelled in `stopRecording()` that calls `stopRecording()` itself, so flag and recorder always end together. And 10s is too short for someone deciding which modifier to assign — 60s is a safety net, 10s is a trap.

Keep the `deinit` change: guard the reset with `if isRecording` (or `if monitor != nil`) so tearing down the *other*, idle recorder during a `.quillDashboardNeedsReload` rebuild cannot clear a live capture.

**Verified:** Verified by walking the code and the sequence.

The class overrides no lifecycle hook: I grepped the whole Sources tree for `resignActive`/`windowWillClose`/`viewDidMoveToWindow`/`resignFirstResponder` and the only hits are in DashboardWindow.swift, DictationSection.swift and OverlayHostView.swift, none of which touch the recorder. `DashboardWindowController.windowWillClose` (DashboardWindow.swift:545) only decrements the window count and flips the activation policy.

Concrete sequence I can walk: open dashboard → Settings → click the hold-key chip (chip lights, reads "Press a key") → click the red close button, or click straight into a terminal, using the mouse only → no local event ever reaches `consume()` → hold ⌥ anywhere → engine returns at line 356, nothing happens, for the rest of the app's lifetime. No test covers it: the only `capturing` hit under Tests/ is HotkeyStateMachineTests.swift:268, which is about audio capture, not hotkey recording. High, not critical.

### A superseded dictation can type its sentence into the next one: LiveTyper has no session identity and the coordinator's session fence is not re-checked across the cleanup await

**Area:** injection

**Failure:** Roman dictates, releases the key, sees "Transcribing", and presses the key again while waiting. Session N's finalising Task passes the session fence at DictationCoordinator.swift:317, then suspends on `await Self.withDeadline(budget, ...)` (line 419) for the full cleanup budget — 250 ms normally, 450 ms when a self-correction cue is present, and by the file's own measurement the deadline expires rather than the call returning in ~89% of cases at 250 ms, so the window is essentially always the full budget. The main actor is free during that suspension. The second press runs `speculativelyBegin()` (sessionID -> N+1), and 120 ms later (`armDelay = 0.12`) `beginDictation()` runs `liveTyper.begin()`, which sets `typed = ""`, `isAbandoned = false`, and captures a fresh targetPID/targetElement — while session N's `finish()` is still pending against that same object. Session N's Task then resumes and calls `self.liveTyper.finish(final_N)` (line 447) with no second fence check. `focusHeld()` passes (same app, same field, freshly captured by N+1), so `apply(final_N, force: true)` computes `edit(from: typed_of_N+1, to: final_N)`. If N+1 has not typed a partial yet, that is deletions 0 / insertion = the whole of final_N, so session N's entire sentence is typed into the document while Roman is mid-way through speaking the next one. If N+1 has typed partials, the diff backspaces over N+1's live text first. `finish` then returns `.inserted`, so the coordinator runs `self.isLive = false` (line 456) — silently killing session N+1's live typing, because `transcriber(didProduce:)` guards on `isLive` — plus `self.undo?.record(final_N)` (overwriting the undo record with the wrong sentence) and `self.timeline.textInserted = Date()` on N+1's timeline. When N+1 finally ends, `isLive` is false, so it takes the else branch, calls `liveTyper.reset()` and pastes its text as well. Net result in the document: session N's sentence typed in the middle of session N+1, N+1's partials partly backspaced, and N+1's full text pasted after. The same window applies with live typing off — `inserter.insert(final_N)` pastes the old sentence into whatever N+1 is being dictated into, which is exactly what the fence's own comment says it exists to prevent ("pasting a sentence from thirty seconds ago into whatever the user is typing in NOW").

**Evidence:** Sources/QuillKit/Injection/LiveTyper.swift:92 `public func begin() -> Bool { cancelPending(); typed = ""; isAbandoned = false; lastUpdate = 0; ... }` — no generation/session token, so a new dictation silently resets the belief a pending `finish()` still depends on. Sources/QuillKit/Injection/LiveTyper.swift:139 `public func finish(_ text: String) -> InsertionResult` — its guards are `isAbandoned` and `focusHeld()`; both pass when the field is unchanged and the caller is a stale session. Sources/QuillKit/App/DictationCoordinator.swift:317 `guard session == self.sessionID else { ... }` (the only fence), :419 `if let better = await Self.withDeadline(budget, operation: { await cleaner.cleanThorough(raw, deadline: budget) })` (unfenced suspension), :446-447 `if self.isLive, !self.liveTyper.isAbandoned { let live = self.liveTyper.finish(final)` (no re-check), :456 `self.isLive = false`, :465 `self.undo?.record(final)`. Window sizes: DictationCoordinator.swift:50 `cleanupDeadline: Duration = .milliseconds(250)`, AIConfig.swift:211 `recommendedCleanupDeadline: Duration = .milliseconds(450)`, HotkeyStateMachine.swift:28 `armDelay: TimeInterval = 0.12`. No test in Tests/QuillKitTests pins the fence across the cleanup await.

**Fix:** The generation-token half is right; the rescue-path half is wrong as written and needs a third piece.

1. Give LiveTyper a generation token (correct as proposed). `begin()` bumps `generation` and returns it; `update`, `finish` and `retract` take the token and no-op — `finish` returning `.failed` — when it does not match. This is the structural fix: a stale session then physically cannot type through a live one.

2. Re-check `guard session == self.sessionID` immediately after the `withDeadline` await, before line 446 (correct as proposed). Everything from :446 to the end of the Task must be inside that fence, not just the insert: `self.isLive = false` (:457), `self.timeline.textInserted` (:458), `self.undo?.record` (:465), the `history.append`, and the trailing `overlay.hide()` all belong to N+1 by then and must not be written by N.

3. Do NOT route the superseded session to the :317 rescue path verbatim, which is what the proposed fix says. That path assumes nothing was typed. Here session N's live partials are already sitting in the user's document, and the record of how many characters they were has been destroyed by N+1's `begin()`, so retracting is impossible (backspaces would eat N+1's characters) and putting `final_N` on the clipboard invites the user to paste a third copy. Instead: (a) hold the live-typed prefix per session rather than in the shared LiveTyper — snapshot `liveTyper.typed` into a local before the `withDeadline` await, so a superseded session knows exactly what it left on screen; (b) record the history row with `insertedText` = that snapshot, and tell the user the sentence stopped where it did rather than offering a clipboard copy that duplicates it.

4. Close the window rather than only detecting it: set a `finalising` flag at the top of the Task and clear it at the end, and have `beginDictation` skip `liveTyper.begin()` (fall back to paste-on-release for that one dictation) while it is set. Otherwise N's orphaned partials and N+1's live stream still interleave in the same field even with the fence in place.

**Verified:** The core mechanism holds up when I walk it myself. The fence at DictationCoordinator.swift:316 is the ONLY session check in the finalising Task, and the Task then suspends at `await Self.withDeadline(budget, ...)` (line ~419) with the main actor free. `endDictation` has already set `isDictating = false; isSpeculating = false`, so `speculativelyBegin()` (line 205, guard `!isDictating, !isSpeculating`) accepts a new key-down during that suspension, bumps `sessionID`, resets `timeline`, and 120 ms later (armDelay 0.12) `beginDictation()` runs `isLive = settings.liveText && liveTyper.begin()` — and `LiveTyper.begin()` (LiveTyper.swift:92-106) unconditionally does `typed = ""; isAbandoned = false` and captures a fresh targetPID/targetElement. Nothing in LiveTyper carries a session/generation token, so the pending `finish()` from session N now points at N+1's state.

When session N resumes there is no re-check: line 446 `if self.isLive, !self.liveTyper.isAbandoned` passes (N+1 just set both), `finish(final_N)` passes `focusHeld()` (freshly captured, same field), and `apply(final_N, force: true)` diffs from N+1's `typed` — not from N's. That is the concrete damage the hunter under-described: session N had ALREADY live-typed its partials into the document during session N, and the record of them was just wiped, so the diff re-types the whole sentence. Net document: [N's live-typed partials][final_N again][final_N+1 pasted at N+1's end]. Roman's sentence appears twice.

The knock-ons are real too and all sit outside the fence: line 457 `self.isLive = false` runs unconditionally, and `transcriber(didProduce:)` guards on `guard isLive, isDictating` (line 647), so N+1's live typing silently dies mid-sentence and N+1 falls to the `else` branch (`liveTyper.reset()` + paste). Line 458 `self.timeline.textInserted` and the `history.append` at the end write into N+1's freshly-reset timeline, and line 465 `self.undo?.record(final_N)` leaves ⌥⌫ pointing at the wrong sentence. The trailing `try? await Task.sleep(900ms); overlay.hide()` also clears N+1's listening HUD.

Nothing documents this as deliberate — the comment at :317 says the opposite, that a superseded session must not insert. No test covers it: only SnippetsTests:315, SelfCorrectionCoordinatorTests:106 and QuickTapTests:138/160 drive the coordinator, and all three run one dictation to completion before the next; nothing in Tests/QuillKitTests references sessionID, supersession, or overlapping sessions, and LiveTyperTests only ever calls `begin()` on a fresh typer.

Two claims in the finding are wrong and they shrink the exposure, which is why I am dropping critical to high:
1. "the window is essentially always the full budget" is a misreading of the 250ms->11% / 450ms->97% comment. Those numbers are for a NIM network round trip, and `NIMCleaner.cleanThorough` (NIMCleaner.swift:156-197) returns the offline answer without any request unless `needsSelfCorrection || needsHomophones` AND `client.isConfigured && client.isReadyToTry`. On the ordinary dictation the await resolves in microseconds and there is no window at all. The exploitable window is the model-pass subset, and inside it is only (suspension − 120 ms) ≈ 150-330 ms, since beginDictation has to land before N resumes.
2. "N+1's full text pasted as well" is framed as loss; it is not. N+1's text still reaches the document once, via the paste in the else branch. The harm is duplication of N's sentence, a dead live-typing session, and a wrong undo record — "wrong text inserted", not "text lost". Narrow race, no data loss: high, not critical.

### resolveParallelRestarts deletes from the FIRST matching restart point, eating clauses the user actually said

**Area:** cleanup / SelfCorrection

**Failure:** Input: "Send it to Noah and then send it to Sam no wait send it to Carlo."

cues() finds "no wait" at tokens 10..12 and marks it a retraction. after = [send,it,to,carlo]; before = [send,it,to,noah,and,then,send,it,to,sam]. Result: "Send it to Carlo." — ten words the user said are gone, including the entire "send it to Noah" instruction, which was never retracted.

### An ordinary noun in front of "at" plus a domain is turned into an email address

**Area:** cleanup / FastCleaner.formatSpokenEmails

**Failure:** Input: "read the docs at netlify.com"
Output: "read the docs@netlify.com"

readDomain accepts "netlify.com" (a real dotted domain), then readLocalPart walks backwards from "at": "docs" is name-like and is not in localPartStopWords, so it is collected; "the" is a stop word and ends the scan. The tokens "docs at netlify.com" are replaced by the single token "docs@netlify.com".

The stop-word list is entirely determiners, pronouns, prepositions and verbs — it has no entry for the common English shape NOUN + "at" + DOMAIN. Every one of these produces a fake address, and the ones with two nouns also glue the words together:

  "my site at romangigliotti.com"            -> "my site@romangigliotti.com"
  "the booking form at kassbarbers.com.au"   -> "the bookingform@kassbarbers.com.au"
  "the pricing page at netlify.com"          -> "the pricingpage@netlify.com"

capitaliseSentences then deliberately leaves the result lowercase because it contains "@", so nothing downstream flags it. These are sentences Roman writes constantly (barber sites, his own portfolio, Netlify). The existing false-fire tests all happen to put a listed verb or determiner directly before "at" ("look at", "hosted at", "are at"), so none of them cover the noun case.

**Evidence:** Sources/QuillKit/Cleanup/TranscriptCleaner.swift:352-369 (readLocalPart) — the only rejections are a sentence-ending token, an empty word, membership in localPartStopWords, or a non-name-like word:

    if localPartStopWords.contains(word.lowercased()) { break }
    guard isNameLike(word) || word.lowercased() == "dot" else { break }
    collected.append(word)

and Sources/QuillKit/Cleanup/TranscriptCleaner.swift:290-291:

    tokens.replaceSubrange(local.firstIndex ... domain.lastIndex,
                           with: ["\(local.text)@\(domain.text)\(trailing)"])

The stop-word set at TranscriptCleaner.swift:392-425 contains no common nouns ("docs", "site", "page", "form", "shop", "repo", "link", "article" are all absent).

**Fix:** Do not use the hunter's fixes as written — each breaks a currently-passing test. (a) Gating on NSSpellChecker over the local part refuses "send the invoice to noah at kass barbers dot com dot au" and "Send To Noah At Gmail Dot Com" if the spell checker knows "noah" (it is an ordinary dictionary/proper name on macOS). (b) Requiring an address-introducing stopper refuses "for example, if I say Roman Gigliotti, 123, at gmail.com, it should work" (the scan stops on "say", which is in the talking-ABOUT-an-address group) and "is it roman at gmail dot com?" (stops on the pronoun "it") — both tests expect the address to be formed.

The correct shape is to make readLocalPart report WHICH token stopped it, and then require one piece of positive evidence before joining, accepting on any of:
  1. the scan stopped on an address-introducing token — "to", "send/sent/invoice/forward/cc/bcc/contact/reach/ping/email/mail", a provider name, a sentence boundary, or the start of the text; or
  2. the domain is a known consumer mail host (gmail/googlemail/outlook/hotmail/yahoo/icloud/proton[mail]) — mail providers are positive evidence on their own; or
  3. the collected local part carries address evidence: a digit (including a folded spoken digit), an internal "dot", or at least one collected token that VocabularyCorrector.isRealEnglishWord (the existing static, memoised, en_AU-first checker at VocabularyCorrector.swift:551) says is NOT ordinary English.
Refuse otherwise — i.e. when the scan stopped on a bare determiner, copula or unlisted verb AND every collected token is ordinary English AND the domain is not a mail provider.

Checked against the existing suite: "Send it to Roman…" (stops on "to"), "invoice noah at kassbarbers.com.au please" and "send the invoice to noah at kass barbers…" (introducer), "my email is roman gigliotti at gmail…", "is it roman at gmail dot com?", "roman at gmail dot com is the address", "that is done. roman at gmail dot com" and the Gmail/Grace/Kingston case (gmail domain, plus a digit) all still fire; "if I say Roman Gigliotti, 123, at gmail.com" fires on the digits. The new refusals are exactly the reported class: "the docs at netlify.com" (stops on "the", "docs" is ordinary English, non-provider domain), "the booking form at kassbarbers.com.au" ("booking" and "form" both ordinary — check per collected token, not the glued string, which would spell-fail as "bookingform"), and "the site is deployed at netlify.com". Cost is negligible: the spell-check branch is only reached when a real domain follows "at" and the scan stopped on a non-introducer.

If a spell-check call inside cleanFast is unacceptable, the minimal stopgap is rules 1+2 alone (introducer or mail-provider domain), which is strictly safer than the current list and still passes every existing test; simply adding nouns to localPartStopWords is the weakest option — it is whack-a-mole against an open class ("docs", "page", "form", "site", "repo", "article", "shop", "deployed", "posted", "published", "up").

**Verified:** Verified by hand-walking formatSpokenEmails on the cited inputs. ### TransformStore treats an unreadable transforms.json as "no transforms" and writes the shipped seed over it on the next run

**Area:** stores

**Failure:** transforms.json is truncated or zero-length (the exact scenario StoreFile was written for: a rename-without-fsync after a panic, or a field a build cannot parse). Roman launches Quill. He then runs any transform at all; TransformEngine.run calls store.recordUse(id) (TransformEngine.swift:205), which calls persist(), which atomically writes the seed array over transforms.json. Every custom transform he wrote — instruction text, triggers, hotkey bindings, length bounds — is gone permanently, and unlike NoteStore/SnippetStore/Vocabulary no salvage copy was ever taken, so there is nothing to recover from. On screen it looks like a factory reset he did not ask for.

**Evidence:** Sources/QuillKit/AI/Transforms.swift:445-453 — `public init(url: URL = TransformStore.defaultURL) { self.url = url; if let data = try? Data(contentsOf: url) { ... items = (try? decoder.decode([Transform].self, from: data)) ?? TransformStore.seed } else { items = TransformStore.seed } }`. There is no `loadFailed` flag, and `persist()` (Sources/QuillKit/AI/Transforms.swift:533-542) writes unconditionally. This is precisely the pattern Sources/QuillKit/Stores/StoreFile.swift:5-21 says every store made and that Tests/QuillKitTests/PasteboardSnapshotTests.swift:149-190 pins for notes, snippets and vocabulary — transforms was never converted and has no such test.

**Fix:** Route the load through StoreFile so the third state exists, and gate the writer on it:

    public init(url: URL = TransformStore.defaultURL) {
        self.url = url
        let decoder = JSONDecoder()
        decoder.dateDecodingStrategy = .iso8601
        switch StoreFile.read([Transform].self, from: url, decoder: decoder) {
        case .missing:           items = TransformStore.seed
        case .decoded(let read): items = read
        case .unreadable:        items = TransformStore.seed; loadFailed = true
        }
    }

plus `private var loadFailed = false` and `guard !loadFailed else { return }` as the first line of persist(). That also gets the salvage copy and the NSLog for free.

Note the one place this should differ from the proposed fix: SnippetStore uses `items = []` on .unreadable because shipping starter snippets would read as a factory reset. Vocabulary.loadOutcome (Vocabulary.swift:74-80) already handles this tension the right way for a store whose seed is load-bearing: return the seed but flag it damaged, so the app keeps working while the writer refuses. Keep the seed in memory, refuse to persist. The data loss is stopped by the persist() guard either way; keeping the seed just avoids trading data loss for a dead feature.

### A device change or disconnect mid-dictation silently truncates the utterance

**Area:** audio

**Failure:** Nothing in the app observes `AVAudioEngineConfigurationChangeNotification`. Per Apple's contract, when the I/O unit sees the input hardware's sample rate or channel count change — AirPods connecting/disconnecting or switching between their 48 kHz and 16 kHz modes when a call starts or ends, a USB interface unplugged, the system default switching — the engine stops and uninitializes itself, taking the installed tap with it. Concretely: Roman is mid-sentence with AirPods, they drop out at the 4-second mark of a 9-second dictation. From that instant no further buffers reach `ingest`, but `AudioCapture.running` is still `true`, the overlay keeps showing the last waveform frame it was given (the meter only updates from tap callbacks, so it freezes rather than reporting anything), and the coordinator has no signal at all. On key release he gets the first four seconds inserted as if that were the whole sentence — text he dictated, silently dropped, with the surviving half reading as a complete thought — or "Nothing was heard" if the drop happened before the recogniser committed. Pick a different microphone in Settings."

No test covers it: every call site of `hotkeyPressed()` in Tests/QuillKitTests (SnippetsTests.swift:315, SelfCorrectionCoordinatorTests.swift:106, QuickTapTests.swift:138/160) is preceded by `hotkeyMayBegin()`, so the defensive branch is never entered. The "speculation deadlock — NOT covered by a test, deliberately" note in SelfCorrectionCoordinatorTests.swift:234 is about cancelDictation, not this.

Severity is overstated, though. The finding implies text that would otherwise have been kept is lost. In the cases that actually throw fast enough to reach this branch — .noInputDevice, .microphoneDenied, TranscriptionError.unavailable — the retry 120 ms later would throw for the same reason, so no audio was capturable either way; what the dead code costs is the honest error at key-down instead of a lying "listening" HUD for the whole utterance and a deferred, sometimes misleading message. Only a genuinely transient .engineFailed (another app holding the device, AirPods switching profile) would recover on retry and save real words. There is also a second, benign route into fail() during speculation — a background rewarm() failure, which fail()'s own comment describes — where the capture session is still live, so beginDictation proceeds over a working session and the dictation completes normally. That makes this "a documented defensive path silently not working" plus a rare recoverable-audio-failure loss, not routine text loss.

The proposed fix is correct as written: calling speculativelyBegin() before flipping isDictating passes both halves of the guard, and the `isSpeculating = false` on line 261 immediately afterwards is harmless because the Task's own guard is `isSpeculating || isDictating`. Minor side effect worth knowing: speculativelyBegin() resets `timeline`, so hotkeyDown is re-stamped at the recovery moment rather than the true key-down, shortening the `held` value used by isChangeOfMind by ~120 ms — irrelevant against the 400 ms tap threshold.

**Failure:** `FastCleaner().cleanFast("Ship the code. Sign the release before you go")` returns "Ship the codesign the release before you go".     // "code" + "sign" is "codesign" only when nothing punctuates between them;

### The audioOwner check and the audio teardown it guards are not atomic, so a finishing dictation can still silence the one that just started

**Area:** SpeechAnalyzerTranscriber — audio-ownership TOCTOU

**Failure:** Two threads, both on the cooperative pool: thread A running `performStop()` for dictation N, thread B running `start()` for dictation N+1. The ownership scheme exists precisely because pulling the tap out from under a newer dictation was measured as '10 of 40 clips produced no transcript at all', but the check and the act are separated. Interleaving: thread A leaves the 2.5s short-utterance grace loop and evaluates `withLock({ audioOwner == session.id })` → true, releases the lock, and is descheduled. Thread B (dictation N+1, started by Roman pressing the trigger again) completes `teardown`, `prepare`, `AnalyzerFeed.make`, sets `audioOwner = N+1` and `self.session = new` under the lock at :189-211, installs `audio.onBuffer` and calls `try audio.start()` — the microphone is now live for dictation N+1. Thread A resumes on the very next line and executes `audio.onBuffer = nil; audio.stop()`, removing the tap and stopping the engine under dictation N+1. Roman speaks a whole sentence and gets nothing: no transcript, no history row, and the coordinator reports '<device> sent no sound at all', blaming his microphone. The window is short in wall-clock terms but it is a plain preemption window on a non-real-time thread, and the grace loop makes thread A a thread that has just come back from a 50ms sleep — exactly the state where the scheduler is most likely to put it behind other work.

**Evidence:** Sources/QuillKit/Transcription/SpeechAnalyzerTranscriber.swift:322-325 — `if withLock({ audioOwner == session.id }) {` / `audio.onBuffer = nil` / `audio.stop()` / `}`. The lock is dropped before the two statements it is supposed to protect. The state it guards is set on the other thread inside one atomic block at :189-197 (`sessionCounter += 1; liveSessionID = sessionCounter; audioOwner = sessionCounter`), so the writer is atomic and only the reader is not.

**Fix:** The proposed `withLock { if audioOwner == session.id { audioOwner = 0; return true }; return false }` does not fix it. Clearing `audioOwner` inside the check changes nothing about the actual interleaving: thread B still writes `audioOwner = N+1` and calls `audio.start()` while thread A is inside `audio.stop()`, because the *side effects* remain outside the lock on both sides. The finding's claim that "a later start() that sets audioOwner = N+1 can then no longer be straddled" is false — that write is exactly what still straddles.

What is needed is one mutex that covers the ownership decision *and* the audio mutation, on both sides, with no await inside the critical section. Two changes:

1. In `start()`, move the claim out of the session-creation block at :189-197 (keep `sessionCounter`/`liveSessionID` there — `ingest()` and the grace loop depend on them) and put `audioOwner` immediately next to the audio start, after the `await` at :215:

    try audioLock.withLock {
        audioOwner = id
        audio.onBuffer = { [weak self] buffer, time in self?.ingest(buffer, at: time, session: id) }
        audio.onLevel  = { [weak self] level in self?.publish(level: level) }
        try audio.start()
    }

2. In `performStop()`, put the check and the teardown in the same critical section:

    audioLock.withLock {
        if audioOwner == session.id {
            audioOwner = 0
            audio.onBuffer = nil
            audio.stop()
        }
    }

Because there is no suspension point inside either block, an NSLock is safe here and the claim/release pair becomes genuinely atomic — B cannot start the engine while A is stopping it, and A cannot stop an engine B has already claimed.

Also fix the two unguarded paths, or the same failure returns through them:
- `teardown(current:)` at :573-574 must take `audioLock` and, when `current != nil`, stop the audio only if `audioOwner == session.id` (clearing it). The `teardown(current: nil)` at the top of `start()` runs before that start claims ownership, so it may stop unconditionally — but still under the lock.
- `cancel()` (:379-388) has no session fence at all: it grabs whatever `self.session` is now, so a late-scheduled change-of-mind cancel can tear down the *next* dictation. It should carry the session id it was issued for and no-op if `self.session` has moved on.

**Verified:** The mechanism is real, though the finding's specific narrative is the least-likely form of it.

Verified facts: `start()` and `performStop()` are plain async methods on a non-actor class, dispatched from the coordinator as two independent detached Tasks (DictationCoordinator.swift:230 spawns `try await transcriber.start()`, :314 spawns `await transcriber.stop()`), and the transcriber's own comment at :50-60 states outright that making start() wait for stop() "fixes the race and breaks the app" — overlap is the documented premise, not speculation. The ownership claim is written atomically at :189-197 (`liveSessionID`/`audioOwner = sessionCounter`), but the reader at :322-325 drops the lock before `audio.onBuffer = nil; audio.stop()`. No test touches SpeechAnalyzerTranscriber concurrency (grep for `audioOwner`/`SpeechAnalyzerTranscriber` across Tests/QuillKitTests returns nothing).

Where the finding's narrative is wrong:
- The grace-loop framing is backwards. If thread A exits the loop via `liveSessionID != session.id` (:311), then `audioOwner` was set to N+1 in the *same* atomic block, so the check at :322 correctly returns false. The grace loop does not make the race more likely; that exit path is the protected one.
- The "thread A is descheduled across all of thread B's start()" interleaving requires A to be preempted between two adjacent instructions for the tens of milliseconds B needs for `teardown` (which itself contains `await withDeadline(1.0) { analyzer.cancelAndFinishNow() }`), `prepare()`, `AnalyzerFeed.make` and `await analyzer.start(inputSequence:)`. Possible, but the narrowest possible version of the window.

The reachable form, which I can walk concretely:
1. A (performStop for N) evaluates `withLock({ audioOwner == session.id })` → true, because B has not yet reached the withLock at :189.
2. A sets `audio.onBuffer = nil` and enters `audio.stop()`. That is `engine.inputNode.removeTap` + `engine.stop()` + `engine.reset()` (AudioCapture.swift:208-233) — real work, single-digit milliseconds, and `running` is not set false until the last line.
3. B, sitting just before :189, runs the withLock (`audioOwner = N+1`), creates the drain task, resumes from `await engine.analyzer.start(inputSequence:)` (fast on an already-prepared analyzer), installs `audio.onBuffer`, and calls `try audio.start()`.
4. `AudioCapture.start()` opens with `guard !running else { return }` (AudioCapture.swift:158) — and `running` is *still true*, because A has not reached line 226 yet. B returns **successfully with no tap installed and no throw**.
5. A finishes: `running = false; prepared = false`.

Net state: engine stopped, no tap, `onBuffer` pointing at session N+1's ingest but never called, and `start()` returned without error so the coordinator shows the listening overlay. Roman speaks a full sentence into a dead microphone, gets an empty transcript, no history row, and the coordinator blames his input device. This is exactly the failure class the ownership scheme was built to kill (the :51-56 comment: "10 of 40 clips produced no transcript at all"), left with a residual few-millisecond window instead of a several-hundred-millisecond one. `AudioCapture.running`/`prepared` are unsynchronised plain Bools, which is what turns the overlap into a silent no-op rather than a visible error.

So: real, but narrower than claimed — a few-ms window inside a several-hundred-ms stop, and only when two dictations overlap. Medium is honest for a race that silently loses an entire dictation in an app used all day; I would not raise it.

The fix in the finding is wrong (see correctedFix). The secondary note about `teardown(current:)` at :573-574 is correct and is arguably the wider hole: `cancel()` (:379-388) takes whatever `self.session` currently is with no session fence and unconditionally stops the audio, so a change-of-mind cancel whose Task is scheduled late can grab and tear down the *next* dictation's session outright.

### Leading punctuation is glued to the word and is deleted whenever the vocabulary corrector replaces that word

**Area:** cleanup / VocabularyCorrector.tokenise

**Failure:** tokenise splits on spaces and peels TRAILING punctuation into `Token.trailing`, but leaves LEADING punctuation inside `Token.word`. On a match, the token is rebuilt as `Token(word: match, trailing: …)` — the leading character is silently dropped.

Input:  he said "Netlify" was down
Output: he said Netlify" was down

Walkthrough: the chunk `"Netlify"` becomes Token(word: `"Netlify`, trailing: `"`). At span 1, bestMatch normalises `"Netlify` to "netlify", which is byte-equal to the normalised term "Netlify", so the exact-match branch returns the term (candidate `"Netlify` != term `Netlify`, so it does not return nil). tokens[index] is overwritten with word "Netlify" and the original leading quote is gone.         let s = String(chunk)

        return Token(word: String(s.dropLast(trailing.count)), trailing: String(trailing))

and the rebuild at Sources/QuillKit/Cleanup/VocabularyCorrector.swift:125:

**Fix:** Direction is right, but two details in the proposed fix are wrong/missing.

1. Peel order in tokenise. Take the trailing run off FIRST, then the leading run off what remains — otherwise a chunk that is entirely punctuation (e.g. a lone `"` or `--`) lands in both fields and gets emitted twice:

    static func tokenise(_ text: String) -> [Token] {
        text.split(separator: " ", omittingEmptySubsequences: true).map { chunk in
            let s = String(chunk)
            let trailing = s.suffix(while: { $0.isPunctuation || $0.isSymbol })
            let core = String(s.dropLast(trailing.count))
            let leading = String(core.prefix(while: { $0.isPunctuation || $0.isSymbol }))
            return Token(leading: leading,
                         word: String(core.dropFirst(leading.count)),
                         trailing: String(trailing))
        }.filter { !$0.word.isEmpty || !$0.trailing.isEmpty || !$0.leading.isEmpty }
    }

   (The existing filter must also admit a leading-only token, or a lone `(` is deleted instead.)

2. The rebuild at line 125 must carry the FIRST token's leading, not the last token's — symmetry with `trailing` is the wrong instinct here, because taking the last token's leading would relocate a quote from the middle of a matched span to its front:

    tokens[index] = Token(leading: window[0].leading,

                          trailing: window[span - 1].trailing)

   Note this still discards leading punctuation on the interior/last tokens of a multi-word span (`fire "store` -> `Firestore`), which is unavoidable when several tokens collapse into one; prepending it to the match would be worse. Worth a comment saying so.

3. Join at line 135 becomes `$0.leading + $0.word + $0.trailing`.

Matching should keep running on the bare word, as the finding says. **Failure:** tokenise keeps chunks that are pure punctuation as Token(word: "", trailing: "-"). isBoundaryWord("") returns false, so such a token is allowed to open a multi-word span, and the span's candidate string is built from `word` only — so the punctuation contributes nothing to matching but is inside the range that gets replaced.

### Nothing observes AVAudioEngineConfigurationChange, so an input-device change mid-dictation silently truncates the transcript

**Area:** transcription / audio capture

**Failure:** Roman is holding the key mid-sentence when the input device changes underneath him — he unplugs a USB mic or headset, or AirPods connect and macOS switches the default input. AVAudioEngine reconfigures its input node and posts AVAudioEngineConfigurationChangeNotification; the tap installed at start() with the old hardware format stops delivering buffers. Nothing in the codebase subscribes to that notification (grep for `ConfigurationChange` finds only a comment), the tap is installed exactly once inside start() with a format read once, and neither AudioCapture nor SpeechAnalyzerTranscriber re-reads `captureFormat` or reinstalls the tap. The dictation carries on from the user's point of view — the overlay is still up, the key is still down — but no further audio reaches the analyzer. On release, stop() returns only the words captured before the switch, so the second half of the sentence is missing with no error and no indication which half was lost; if the switch happened before any word was recognised, stop() burns the 2.5s short-utterance grace waiting for audio that can no longer arrive and then returns "Nothing was heard".

**Evidence:** Sources/QuillKit/Audio/AudioCapture.swift:183-196 — `input.installTap(onBus: 0, bufferSize: 1024, format: format)` is the only tap installation, with `format` read once at :177; :142-155 selectConfiguredInputDevice runs only from prepare()/start(); AudioCapture.swift:97 mentions `AVAudioEngineConfigurationChange` only inside a comment about why it did not fix the inputFormat-vs-outputFormat crash. `grep -rn --include='*.swift' ConfigurationChange Sources` returns that comment and nothing else — there is no NotificationCenter observer anywhere in the package.

**Fix:** Direction is right, but the fix as written would introduce a race and overstates the feed work.

Observe `AVAudioEngine.configurationChangeNotification` in AudioCapture, but do not reconfigure inline on the notification thread. `running` and `prepared` are plain unsynchronised vars touched by prepare()/start()/stop(), which run off whichever thread drives the dictation; a handler mutating engine state concurrently races start() and stop() — pulling the tap out from under a stop() already in progress, or reinstalling one after it. Serialise the whole thing: give AudioCapture a private serial queue, hop prepare()/start()/stop() and the notification handler onto it, and make the handler a no-op unless `running` is still true.

On that queue, when running: removeTap(onBus: 0), re-run selectConfiguredInputDevice(), re-read `captureFormat` (nil ⇒ give up and report rather than install), reinstall the tap at the new format, and restart the engine — the engine has uninitialised itself, so `engine.prepare()` then `engine.start()`, and treat a throw as a reportable error rather than swallowing it. Do not call the existing stop(), which would engine.reset() and drop the audio already queued for this dictation.

The feed only needs replacing on the macOS 26 path: `ModernAnalyzerFeed` wraps `AnalyzerInputConverter`, which takes whatever buffer it is handed (AnalyzerFeed.swift:48-51), so on macOS 27 reinstalling the tap is sufficient. `LegacyAnalyzerFeed` is constructed `from: captureFormat` (AnalyzerFeed.swift:33), so if the new format differs the transcriber needs a fresh feed for the remainder of the session — and note that means a fresh resampler mid-utterance, which the comment at AnalyzerFeed.swift:61-64 says puts a click at the boundary the recogniser hears as consonants; on that path the honest answer is to stop the session and surface the interruption.

Whatever the recovery path, the silent part is the real bug: the transcriber should mark the session as audio-interrupted so the coordinator can tell Roman the microphone changed mid-sentence, while still inserting and recording the text it did get. Trimming a sentence in half with no indication is worse than an error beside the text.

**Verified:** Confirmed, with one severity correction and one correction to the fix.

The code claims check out. `AudioCapture.start()` (Sources/QuillKit/Audio/AudioCapture.swift:157-206) reads `captureFormat` exactly once at :177 and installs the one and only tap at :183 with that format. `selectConfiguredInputDevice()` (:142) is called only from `prepare()` (:124) and `start()` (:168). `grep -rn addObserver Sources/QuillKit` returns AppDelegate, DashboardWindow, three dashboard sections, InsertionUndo and OverlayController — none of them audio; the only occurrence of `AVAudioEngineConfigurationChange` in the tree is inside the doc comment at AudioCapture.swift:97, and that comment rejects the notification as a fix for the *inputFormat-vs-outputFormat install crash*, not as a decision about mid-session device changes. So there is no deliberate-decision comment covering this, and no test touches AudioCapture at all (no file in Tests/QuillKitTests references AudioCapture or AudioSource).

The mechanism is asserted by this codebase itself, measured: AudioCapture.swift:133-136 — "changing the device changes the node's output format underneath you, and a tap installed with the old format silently delivers nothing." That is exactly the mid-dictation case, only arrived at from the outside.

Walking the failure with default settings:
1. QuillSettings.Values.inputDeviceUID defaults to nil (QuillSettings.swift:84), so `selectConfiguredInputDevice()` returns at its first `guard` and the engine's input node follows the system default device. The default configuration is the vulnerable one.
2. Key-down → SpeechAnalyzerTranscriber.start() (:177-183): audio.prepare(), captureFormat read once (48 kHz), AnalyzerFeed built against it, audio.start() installs the tap at 48 kHz, engine starts.
3. Two seconds into a seven-second sentence his AirPods finish connecting and macOS moves the default input to them at a different rate/channel count. The engine's I/O unit observes the change, stops itself and posts the notification nobody listens for.
4. Nothing re-reads `captureFormat`, nothing reinstalls the tap: both live only inside prepare()/start(). `running` stays true. The remaining five seconds never reach the analyzer.
5. Key-up → endDictation (DictationCoordinator.swift:279+): held ≈7s and sawLevels true, so `isChangeOfMind` is false. performStop() (SpeechAnalyzerTranscriber.swift:258+) sees non-empty `settled`, skips the grace, drains, returns the truncated first half.
6. Non-empty transcript sails past the empty guard at :359, gets cleaned, inserted at the caret and written to history. No error, no marker. The only cue is the overlay meter freezing at its last value, which he will not catch mid-sentence.

Two details in the finding are slightly off but do not change the verdict. The "burns the 2.5s grace" branch requires `session.heardAnything` (SpeechAnalyzerTranscriber.swift:303) — true only if audio above the silence floor arrived before the switch, so it applies to a switch after speech began, not to one before any audio at all. And on macOS 27 the feed is `ModernAnalyzerFeed`, whose `AnalyzerInputConverter` is not locked to a capture format (AnalyzerFeed.swift:29-31, 48-51); only the macOS 26 `LegacyAnalyzerFeed` is built `from: captureFormat` and would need rebuilding.

Severity: medium is inflated. The trigger has to land inside a two-to-ten-second key hold, the damage is one truncated dictation that is visibly incomplete, and the next press recovers on its own because stop() clears running/prepared and start() re-reads the format. That is a real loss of dictated words — the thing this codebase says it may never do — but it is rare and self-healing, so low.
